## 1. 创意与玩法

### 创作灵感

灵感来自一次与 AI 聊天的"翻车"体验：我随口说了一句假话，十几轮之后 AI 还记得并拿来反驳我——那一刻我突然意识到，**"AI 会记忆"这件事本身，就能做成玩法**。

大多数游戏里的 NPC 是"金鱼脑"：问过的每一句都蒸发。如果把 NPC 的记忆做成可视化的、可被玩家利用与对抗的系统，AI 就不再是黑盒，而是游戏机制本身。

### 核心玩法

《第七位证人》是一款限时审讯推理游戏：雾隐镇百年自鸣钟的机芯昨夜被盗，午夜钟声少敲了一下。玩家扮演外来侦探，限时 **60 分钟**（游戏内时间）审讯 4 名嫌疑人，从 5 人中指认真凶——而真凶根本不在审讯名单上。

```
选择审讯对象 → 自由提问(-1min) → NPC 记忆图谱更新
     ↑                    ↓
     └──── 指认真凶 ← 出示证据(-2min) → 命中=撬开秘密+关键线索
```

### 作品亮点

- **🧠 会记忆的 NPC**：每名嫌疑人由大模型驱动，拥有性格人设、隐藏秘密、信任度与情绪；你问过的每一句话都会进入他的"记忆图谱"，实时可视化他记得什么、隐瞒什么。
- **🧾 证据质询强制剧情**：5 件证物各有其主，"对的证据 × 对的人"才触发坦白，解锁 4 条关键线索；线索数决定结局评级 S/A/B，指认错误则是冤案结局。
- **🔗 链式多供应商 + 离线兜底，评审现场永不断线**：台词链按 **主供应商（qwen3.8-27b）→ 备供应商（sensenova-6.8-flash）→ MockLLM 规则引擎** 逐级组装，任何一环失败当次自动切到下一环（逐调用回退，非启动时二选一）；即使全部在线通道失效，纯离线也能完整通关——这不是设计假设，是我们在 429 限流事故中实测过的（见第 4 节）。

## 2. 创作过程

整个作品从零到上线用了 1 天（2026-11-13），开发模式为 **"人定玩法与验收，AI 结对写码"**：

| 步骤 | 产出 | 分工 |
|---|---|---|
| ① 真相链剧本 | 凶手沈墨白的完整作案链（化名住店→定制钩爪钥匙→蜡模配钥匙→23:47 潜入→被侦探目击），4 条关键线索与 4 个坦白台词一一对应 | 人出案件框架，AI 打磨台词与民国小镇口吻 |
| ② 游戏数据层 | `game_data.py`：案件/4 名 NPC（性格、秘密、话题台词库）/5 件证物/结局文本 | AI 生成，人审"证词缝隙"逻辑自洽 |
| ③ 游戏引擎 | `npc_engine.py`：信任/情绪/记忆状态机、证据质询、指认结算 | AI 实现，人定数值（60min/1min/2min、信任增减） |
| ④ LLM 链式多供应商 | `llm_client.py`：MockLLM 规则引擎 + 主/备 OpenAI 兼容供应商 + 魔搭 legacy 通道，逐调用兜底 | AI 实现+实测 |
| ⑤ UI | Gradio Blocks：审讯区/记忆图谱/线索板/证物栏/结案指认 | AI 实现，人提交互修改（快捷提问直接发送等） |
| ⑥ 部署 | 魔搭创空间（Docker SDK），全流程公网验收 | AI 自动化完成 |

**AI 与个人分别完成的工作**：代码、剧本台词、部署脚本与自测均由 AI 结对完成；玩法设计决策（记忆图谱作为核心卖点、证物×NPC 矩阵、时间惩罚数值）、每一轮验收（全流程试玩、边界结局测试）与"永不断线"的评审导向由人把握。

## 3. 工具应用与体验

### 链式多供应商 LLM（OpenAI 兼容接口）

- **调用的模型**：主 `qwen3.8-27b`，备 `sensenova-6.8-flash`（均为 OpenAI 兼容接口；早期原型用魔搭 API-Inference `Qwen/Qwen3.8-Flash-Next`，现保留为 legacy 兜底通道）。
- **具体用途**：NPC 台词实时生成。System Prompt 注入角色人设、秘密、信任度、记忆图谱摘要与"全镇共识"（沈师傅已出城），要求严格输出 JSON（dialogue/emotion/trust_change），情绪与信任度变化回写游戏引擎；供应商侧密钥只走环境变量，不进代码库。
- **效果**：实测延迟 1–3 秒/次；台词符合民国小镇口吻，能保持背景一致（多次提问都围绕"上礼拜一出城去如意镇"展开，不自相矛盾）；输出 JSON 解析成功率高，对 `<think>` 包裹与代码围栏做了容错。
- **运行记录**：① 开发期实测——"案发当晚你在哪里？"→ 2.6s 返回"我？在炉前打铁呢！火星子溅得满地都是……"；② 上线后公网端到端复测（11.14，经创空间线上 Gradio API 实问王大锤"你最后一次见到沈师傅是什么时候"）→ 2 秒内返回动态台词"看着他的车屁股冒烟才转身"，确认线上环境变量注入生效、主链真实在线生成（截图见发布稿）。

### 魔搭创空间（部署）

- 使用 Docker SDK（`python:3.10-slim` + 锁定 `gradio==6.32.0`），构建约 1–2.5 分钟即 Running；公网双地址（`ms.show` + 创空间页）健康检查全 200，`/config` 探针确认组件存活。推送即自动构建，全流程 75 秒完成过一次热更新。
- 代码托管 GitHub 后接入 **CI/CD 自动部署**：push 到 main 触发 GitHub Actions，自动同步代码到创空间仓库并调用部署接口，再推代码即热更新，无需手动操作。
- LLM 供应商密钥通过创空间环境变量注入（不进代码库）；上线后经公网 API 实测在线台词链路真实生效（见上文运行记录②）。

## 4. 问题与解决

**问题：在线 LLM 限流（429 insufficient balance）会打断游戏**

- **现象**：接入真模型后连续提问，第 3 问命中魔搭 API-Inference 额度限制，抛出 `RateLimitError: 429`。若不做处理，玩家将看到报错、审讯流程中断——对一款"评审现场必演示"的参赛作品是致命的。
- **解决过程**：
  1. 把 `get_llm()` 从"启动时二选一"改为 **逐调用兜底**：每次提问先走在线模型，任何异常（限流、超时、解析失败）当次自动回退下一级，并在控制台记录——这一思路后续进一步演进为 **链式多供应商**（主 → 备 → Mock），单一供应商故障不再影响可用性；
  2. 离线 MockLLM 覆盖全部话题分支与 4 条坦白线，保证**纯离线也能完整通关**；
  3. 信任度/记忆/时间等状态全部由引擎维护，不依赖 LLM——即使台词降级，玩法数据仍连续。
- **改进效果（前后对比）**：
  - 改前：第 3 问抛异常，对话流中断；
  - 改后：第 3 问 1.6 秒内无缝切到离线台词（"钟楼侧门的钥匙？拢共三把……"），玩家无感知，时钟/信任度/记忆图谱照常更新。实测 429 后连续通关，结局评级与线索计数完全正确。

**附带修复**：gradio 4.44 JSON schema 崩溃补丁（bool schema → Any）、创空间容器绑定 `0.0.0.0:7860`、Qwen3 系 `<think>` 输出剥离。

## 5. 经验总结

**可复用的经验**：

1. **AI 应用要做"逐调用兜底"而不是"启动时二选一"**——在线能力随时可能抖动，把降级粒度做到单次调用，用户体验才无感。
2. **让引擎持有状态、LLM 只负责台词**——JSON 结构化输出 + 容错解析 + 数值钳制，LLM 再怎么抽风，游戏状态不会脏。
3. **参赛作品的部署要锁版本**（`gradio==6.32.0`），评审现场不赌平台默认环境的漂移。
4. **"AI 的记忆"可以是很便宜的原生玩法**：不需要 RAG 和向量库，一个 `memories` 列表 + 可视化面板，玩家就能"看见 AI 在想什么"。

**后续想改进的方向**：

- NPC 长期记忆持久化（跨局记住玩家的审讯风格，二周目台词变化）
- 多供应商链路健康度观测（后台定时探活，把"出错才切换"升级为"预防性切换"）
- 多案件/团伙作案剧本，支持玩家伪造证据的对抗玩法
- 演示视频与语音化台词（TTS）提升传播效果
